# HTTP 中的 “对头阻塞”（Head-of-Line Blocking，HOB）

HTTP 的 “对头阻塞”（Head-of-Line Blocking，简称 HOB）是指在 HTTP 协议中，由于请求 / 响应的串行处理机制，导致一个请求 / 响应的延迟或阻塞会影响后续所有请求 / 响应处理的现象。这种问题在不同 HTTP 版本中表现形式不同，核心原因与协议的传输机制密切相关。

## 1. HTTP/1.1 中的对头阻塞

HTTP/1.1 是应用最广泛的传统版本，其对头阻塞主要体现在两个层面：

### TCP 层的对头阻塞

HTTP/1.1 基于 TCP 协议传输，而 TCP 是 “字节流有序传输” 协议：接收方必须按顺序处理字节流，若中间某个数据包丢失或延迟，后续数据包即使已到达，也需等待丢失的数据包重传后才能继续处理。此时，即使 HTTP 请求本身没问题，TCP 层的阻塞也会导致所有 HTTP 请求 / 响应被卡住。

### HTTP 层的串行请求限制

HTTP/1.1 虽支持 “持久连接”（Keep-Alive）复用 TCP 连接，但默认仍需串行发送请求（即前一个请求的响应完全返回后，才能发送下一个请求）。即使通过 “管道化（Pipelining）” 技术允许并行发送多个请求，响应仍需按请求顺序返回（FIFO），若首个请求的响应延迟（如服务器处理慢），后续响应即使已生成，也必须排队等待，导致后续请求被阻塞。

## 2. HTTP/2 中的对头阻塞缓解（但未完全解决）

HTTP/2 通过 “多路复用” 技术优化了 HTTP 层的串行问题：
多个请求 / 响应可通过同一 TCP 连接并行传输（无需排队），每个请求被拆分为独立的 “帧”，通过 “流 ID” 标识归属，接收方可按流 ID 重组数据，避免了 HTTP 层的串行阻塞。

但 TCP 层的对头阻塞仍存在：
HTTP/2 仍基于 TCP 传输，若某个帧对应的 TCP 数据包丢失，整个 TCP 连接上的所有流（请求）都会被阻塞，需等待该数据包重传后才能继续处理。因此，TCP 层的对头阻塞仍是 HTTP/2 的性能瓶颈。

## 3. HTTP/3 对于对头阻塞的解决

HTTP/3 彻底抛弃 TCP，改用 QUIC 协议（基于 UDP），从根本上解决了对头阻塞：
QUIC 为每个 HTTP 请求分配独立的 “流”，流之间完全隔离。若某个流的数据包丢失，仅影响该流本身，其他流可正常传输和处理，彻底避免了 TCP 层的对头阻塞。

## 总结

对头阻塞的本质是 “串行依赖导致的连锁阻塞”，不同 HTTP 版本的优化思路如下：

- HTTP/1.1：因 TCP 依赖和串行请求，对头阻塞问题最严重；
- HTTP/2：通过多路复用解决 HTTP 层阻塞，但受限于 TCP，仍有底层阻塞；
- HTTP/3：基于 QUIC 的流隔离，彻底消除了对头阻塞，大幅提升传输效率。
